# Конспект: Broken Access Control (Нарушение контроля доступа)

---

## 1. Базовые понятия

| Термин | Расшифровка | Суть |
|---|---|---|
| **Authentication** | Аутентификация | Проверка, **кто ты** (логин/пароль, MFA, биометрия) |
| **Authorization** | Авторизация | Проверка, **что тебе можно** (роли, права, атрибуты) |
| **Access Control** | Контроль доступа | Механизм, который решает, кому что разрешено |
| **Broken Access Control** | Нарушение контроля доступа | Уязвимость, при которой приложение **неправильно** проверяет права |

**Ключевое правило:** Аутентификация без авторизации бесполезна. Ты доказал, кто ты — но система не проверила, что тебе можно.

---

## 2. Почему это важно

- **№1 в OWASP Top 10 (2021)** — самая распространённая критическая уязвимость.
- Позволяет: читать чужие данные, менять чужие профили, выполнять админские действия, обрушить систему.
- Часто **не требует** сложных эксплойтов — достаточно поменять ID в URL.

---

## 3. Все подкатегории

### 3.1. IDOR (Insecure Direct Object Reference)

**Суть:** Прямой доступ к чужому **объекту** по ID без проверки владельца.

**Пример:** `GET /api/users/2` — Алиса видит профиль Боба.

**Где может быть ID:** URL-путь, query-параметр, тело POST, заголовок, кука, JWT.

---

### 3.2. BOLA (Broken Object Level Authorization)

**Суть:** То же, что IDOR, но в контексте **API**. Современный термин из OWASP API Security Top 10.

---

### 3.3. BFLA (Broken Function Level Authorization)

**Суть:** Пользователь выполняет **функцию** (действие), которая ему не разрешена.

**Пример:** Обычный юзер вызывает `DELETE /api/admin/users/2`.

**Отличие от IDOR:**

| Критерий | IDOR | BFLA |
|---|---|---|
| Что нарушено | Доступ к **объекту** | Доступ к **функции** |
| Вопрос | «Можно ли тебе видеть **этот объект**?» | «Можно ли тебе **выполнить это действие**?» |
| Пример | `GET /api/users/2` | `DELETE /api/admin/users/2` |

---

### 3.4. Mass Assignment (Массовое присвоение)

**Суть:** Приложение копирует **все** поля из запроса в объект, включая запрещённые.

**Пример:** `Object.assign(user, req.body)` — Алиса отправляет `{ "role": "admin" }` и становится админом.

**Фикс:** Явный allowlist разрешённых полей.

---

### 3.5. CORS Misconfiguration

**Суть:** Слишком широкие правила CORS (Cross-Origin Resource Sharing — Совместное использование ресурсов между разными источниками).

**Опасная комбинация:** `Allow-Origin: <отражение любого Origin>` + `Allow-Credentials: true`.

**Фикс:** Белый список доверенных Origin.

---

### 3.6. Forced Browsing (Принудительный обход)

**Суть:** Защищённая страница открывается по прямому URL, потому что защита была только на уровне скрытия ссылок.

**Пример:** `/admin/panel` без `authenticate` и `requireAdmin`.

**Фикс:** Проверять права на **сервере** для каждого защищённого ресурса.

---

### 3.7. JWT Misconfiguration

**Типичные ошибки:**
- Слабый секрет (подбирается брутфорсом).
- Принятие `alg: "none"` (токен без подписи).
- Отсутствие явного указания алгоритма в `jwt.verify()`.
- Доверие полю `role` внутри токена без проверки в БД.

**Фикс:** Длинный случайный секрет, явный `algorithms: ['HS256']`, короткий `expiresIn`.

## 4. Сводная таблица

| Уязвимость | Что нарушено | Пример | Фикс |
|---|---|---|---|
| **IDOR** | Объект | `/api/users/2` | Проверка `req.user.id === userId` |
| **BOLA** | Объект (API) | `GET /api/orders/98765` | То же |
| **BFLA** | Функция | `DELETE /api/admin/users/2` | `requireAdmin` middleware |
| **Mass Assignment** | Поля объекта | `{ "role": "admin" }` | Allowlist полей |
| **CORS Misconfig** | Политика браузера | `Allow-Origin: *` + credentials | Белый список Origin |
| **Forced Browsing** | Ресурс | `/admin/panel` без auth | `authenticate` + `requireAdmin` |
| **JWT Misconfig** | Токен | Слабый секрет, `alg: none` | Сильный секрет, явный алгоритм |

---

## 5. Принципы защиты

1. **Deny by default** — запрещать по умолчанию, разрешать явно.
2. **Проверять на сервере** — клиенту доверять нельзя.
3. **Не доверять ID из запроса** — брать `req.user.id` из токена/сессии.
4. **Allowlist полей** — не копировать `req.body` целиком.
5. **RBAC/ABAC** — использовать модели управления доступом.
6. **Логировать отказы** — для обнаружения атак и аудита.
7. **Защита в глубину** — несколько слоёв проверок (роль + владелец + бизнес-правила).
8. **Тестировать** — SAST (Static Application Security Testing — статическое тестирование) + DAST (Dynamic Application Security Testing — динамическое тестирование).

## 6. Чек-лист для поиска BAC в коде

- [ ] Есть ли эндпоинты без `authenticate`?
- [ ] Проверяется ли роль (`requireAdmin`) на админских эндпоинтах?
- [ ] Проверяется ли владелец объекта (`req.user.id === userId`)?
- [ ] Берётся ли ID из токена, а не из запроса?
- [ ] Используется ли `Object.assign` / spread с `req.body`?
- [ ] Указан ли явно алгоритм в `jwt.verify()`?
- [ ] Сильный ли секрет JWT?
- [ ] Есть ли белый список CORS?
- [ ] Возвращаются ли чувствительные поля (пароли, балансы)?
- [ ] Есть ли проверки от самоудаления / последнего админа?
- [ ] Есть ли soft delete и логирование?

---

## 7. Как различать типы (шпаргалка)

| Вопрос | Ответ «да» → |
|---|---|
| Получил доступ к **чужому объекту**? | **IDOR / BOLA** |
| Выполнил **действие**, которое не разрешено? | **BFLA** |
| Изменил **запрещённое поле**? | **Mass Assignment** |
| Открыл страницу **без аутентификации**? | **Forced Browsing** |
| Использовал **слабый JWT**? | **JWT Misconfig** |
| **Любой сайт** читает ответы API? | **CORS Misconfig** |

---

## 8. Ключевые уроки

1. **IDOR vs BFLA:** объект vs функция.
2. **Mass Assignment — отдельный тип:** не IDOR, не BFLA.
3. **Одна строка — несколько уязвимостей:** `Object.assign(user, req.body)` = IDOR + Mass Assignment.
4. **Последствия важны:** BFLA может привести к DoS (Denial of Service — Отказ в обслуживании).
5. **Защита в глубину:** мало одного `requireAdmin` — нужны проверки самоудаления, последнего админа, soft delete, аудита.
